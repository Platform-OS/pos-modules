# 01 — Settled decisions

Do not reopen these unless new evidence contradicts them; record the evidence in `backlog/decisions/` if it does.

| ID | Decision | Why | Decided by |
|---|---|---|---|
| D-1 | Build a **module** (`pos-module-support`, machine name `support`) in Platform-OS/pos-modules first; our Zoho replacement is its first installation | Partners and AI tools reuse modules; Slack thread 2026-10-21 (Adam, JJ) | Leadership |
| D-2 | All UI lives in a **standalone section at `/support-desk/*`** with the module's own layout and sign-in; it is not part of, and does not depend on, a host admin area (D-21) | Works for apps with or without users or an admin; external agents must not need host admin rights | Artur (2026-10-28) |
| D-3 | **Provider-neutral email layer, configured per installation at deploy time.** The module defines one adapter contract (`parse_inbound`, `send`, `parse_events`); the MVP ships the **SendGrid** adapter (Inbound Parse in, v3 Mail Send out). Provider, API key, inbound domain/address, secrets and from-addresses are set by the install generator and Settings → Email — never in module code. Our installation uses the existing pOS SendGrid account and `in.support.platformos.com` | Partners have their own SendGrid accounts or other providers | Artur (2026-10-27) |
| D-4 | Threading cascade: signed reply token in the recipient address → `In-Reply-To`/`References` against stored Message-IDs (kept forever) → `[#number]` subject token with sender check → new ticket | Research: header-only threading fails (Zendesk 30-day window, iOS replies, Google Groups) | Spec |
| D-5 | Statuses are admin-defined labels over **six fixed categories** (`new`, `open`, `pending`, `on_hold`, `solved`, `closed`); behaviour keys off the category | Industry norm; makes SLA pauses and reopen rules generic | PRD |
| D-6 | **Confirmation** is in the `solved` category (SLA stopped, customer reply reopens); what happens when the customer never replies is D-18 | PRD | Artur |
| D-7 | Priorities **P0–P3**; SLA targets per priority; clock runs in `new`/`open`, pauses in `pending`/`on_hold`, stops in `solved`/`closed` | PRD SL-1..SL-7 | PRD |
| D-8 | Assignment **option B only**: the Available agent in the ticket's department with the fewest open tickets; ties to least-recently assigned; per-agent cap (default 15). Safety net: managers alerted after 15 min (5 for P0), on-duty manager assigned after 30 min | User choice 2026-10-27 | Artur |
| D-9 | `/support-desk` is its **own PWA**: manifest and service worker scoped to `/support-desk/`; push via pos-module-push-notifications | User requirement 2026-10-27 | Artur |
| D-10 | Agent notifications for new ticket in my departments, assigned to me, customer reply, @mention, SLA due in 15 min, SLA breached, still unassigned, new P0 — **push and email, all on by default**, each switchable per person in the profile; plus "Pause all" | User requirement 2026-10-27 | Artur |
| D-11 | **White-label**: styled only with common-styling `--pos-*` variables and classes; host stylesheet arrives through the `headscripts` hook; name, logos, icon and theme colour from a `support_branding` hook; overrides in Branding settings; status/priority/SLA colours fixed | User requirement 2026-10-27 | Artur |
| D-12 | *(Revised 2026-10-28, replaces "patch the host permissions file")* Access is **module-owned**: a `team_member` record per profile (role agent / manager / admin, departments, state) is the only thing that grants desk access, checked by `modules/support/can/desk` as the `access_callback` of the user module's `can_do_or_unauthorized`. The host's permissions file is never edited | pos-module-mcp precedent (`mcp_access`); host role names differ (platformOS Community has no `admin` role); SupportCandy/Fluent Support/django-helpdesk keep support access separate from site admin | Artur (2026-10-28) |
| D-13 | *(Revised 2026-10-28, decision-11)* Live updates and presence use **platformOS's own WebSocket channels** (Action Cable), the way pos-module-chat does: channel `support` with rooms `queue-<department_id>`, `ticket-<ticket_id>`, `profile-<profile_id>`; server broadcasts with `channel_send_message`; `subscribed` and `receive` each check membership and department scope. pos-module-websocket is not on the marketplace, so it is not a dependency | `pos-cli modules install` failed: websocket not in the registry | Spec |
| D-14 | SLA and auto-close timers use **delayed `background` jobs** per ticket plus a self-rescheduling sweep job; no cron exists | platformOS has `background … delay:` and no scheduler | Spec |
| D-15 | Iterations 4–5 (AI) expose support operations as tools through **pos-module-mcp**; customer-facing or GitHub-creating actions go through its approval gate | Filip's verified OAuth flow; "a human approves" rule in PRD | Spec |
| D-16 | Development is done by Claude with the **Agent Playbook loop** (validate → write → deploy-start → verify) and backlog.md provenance | Team practice | Spec |
| D-18 | Confirmation behaviour is an **admin setting** (`confirmation_mode`): `auto_close` (**default**) closes the ticket when the waiting period ends; `keep_open` leaves it in Confirmation and notifies the assignee once (managers if unassigned) when the waiting period ends (event `confirm_wait`, push + email, switchable per person). Waiting period `confirmation_wait_days` 1–28, default 7 | Support manager's choice per installation | Artur (2026-10-27) |
| D-19 | **Zoho migration is not part of the MVP build.** It is its own step right after the MVP ships (TASK-28), before Zoho is switched off | Keep the first iteration small | Artur (2026-10-27) |
| D-20 | **Feature branch in pos-modules**: develop in `Platform-OS/pos-modules` on `feature/pos-module-support`, deploy to our instance, test there; one PR to `master` for Maciek and Filip when everything passes. No PRs, issues or review requests in pos-modules before that; progress on a private org Project with draft items (13-delivery-workflow.md) | Artur's choice; keeps review for the finished MVP | Artur (2026-10-27) |
| D-21 | *(Revised 2026-10-28)* **Standalone desk plus an optional admin-menu entry (option C).** Desk pages use `layout: modules/support/support` and `metadata.permission`; no embedded mode and no `LAYOUT` constant. The module also ships `pages/admin/support.liquid` (`metadata.menu`, `permission: admin_pages.view`, `relative_path`) that only redirects to `/support-desk`, so hosts that build admin menus from `admin_pages` list Support; the generator can remove it | Host admin layouts bounce users without `admin_pages.view` (platformOS Community `layouts/admin`), which would lock out support-only agents | Artur (2026-10-28) |
| D-22 | **Profiles, not users** (pos-module-user rule): every agent, assignee, author and owner reference is a user-module **profile id**; permissions are checked on profiles | Consistent with RBAC in the user module | Spec |
| D-23 | **Security posture** modelled on pos-module-mcp: deny by default (no page without an explicit permission), fail closed on any lookup miss, 404 instead of 403 where a 403 would reveal that a ticket exists, GraphQL arguments always typed variables (never interpolated), module boundary checked by a static CI gate | Highest standard in the repo | Spec |
| D-24 | **One access model, five ways in, one record.** Ways to become a member: (1) install generator — first support admin, plus recovery constant `modules/support/ADMIN_EMAILS`; (2) invite (D-25); (3) **Request access** — a signed-in non-member sees "You don't have access to Support" with a button; support admins approve with role and departments; (4) optional **role mapping** setting (host role → support role, off by default), membership created on first visit; (5) **superadmin** → support admin, created on first visit. Host admins without membership get no ticket access. Every membership records `source` and `created_by`; Disable removes access at once, and mapping never recreates a disabled membership | Least privilege for customer data; single list in Settings → Team; one audit trail | Artur (2026-10-28) |
| D-25 | **Invites.** Apps with users: Settings → Team → Add member with two tabs — **Pick existing staff** (profiles whose roles grant `admin_pages.view`, the user module's standard admin permission, so the role name does not matter; admins can edit the list of staff roles; tab hidden when no role grants it) and **Invite external** (email). Apps without users: only Invite by email. An external invitee gets an account created with **`roles: []`** (never `USER_DEFAULT_ROLE`, which would give e.g. community `member` access) → support-only. If the email already has an account, the membership is added to it. Invite email links to `/support-desk/invites/:id?token=…` (7-day expiry, single use, token stored as a digest) to set a password; accepting signs them in to the queue | Covers marketing sites, apps with users, apps whose admin role is not `admin`; `pos-module-user-invites` is community-shaped (CSV, `admin/community`, redirect to `/onboarding`, no role) | Artur (2026-10-28) |
| D-26 | **Board view** next to the list: one column per status in status order (Closed and Spam hidden unless "Show closed"); drag a card to another column to change status, every card also has a "Move to" menu (works without JavaScript). Inside a column cards are **sorted automatically: priority P0→P3, then newest first** — no manual ordering | JJ's build; Artur 2026-10-28 | Artur (2026-10-28) |
| D-27 | **Blocklist**: support admins block an address or a whole domain (with reason); inbound mail from a blocked sender is refused before anything is stored; "Mark as spam" on a ticket moves it to Spam and blocks that one address (never the domain); unblock in Settings → Blocklist | JJ's build; protects agents from abuse and loops | Artur (2026-10-28) |
| D-28 | **Inbound secret rotation** in Settings → Email: "Rotate secret" generates a new `INBOUND_SECRET` (and `EVENTS_SECRET`), updates the provider through its API (SendGrid `PATCH /v3/user/webhooks/parse/settings/{hostname}`), and keeps accepting the previous secret for 24 h so no mail is lost; the URL is masked with Reveal. The Event Webhook is the module's own (created with `POST /v3/user/webhooks/event/settings`, id stored, updated by id), because the account may already use another one (decision-9) | JJ's build has regenerate; ours avoids the outage because we hold the API key | Artur (2026-10-28) |
| D-17 | Iteration order after the MVP: GitHub status loop (I2) → chat + portal + offline (I3) → AI first responder + copilot (I4) → AI triage to GitHub (I5) | High-level PRD roadmap | PRD |
