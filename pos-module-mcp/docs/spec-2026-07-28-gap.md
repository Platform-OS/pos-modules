# MCP `2026-07-28` — gap analysis & migration

**Status of this module:** dual-era. It serves **legacy** `2025-06-18` clients (the
`initialize` handshake) and **modern** `2026-07-28` clients (every request declares its
revision in `_meta`), deciding per request. A version-less request is legacy and behaves
exactly as before. This doc maps the `2026-07-28` changes to the engine, records what
shipped, and lists what remains.

> Source: the `2026-07-28` specification — `schema/2026-07-28/schema.ts`,
> `basic/versioning`, `basic/transports/streamable-http` and the Tasks extension overview
> in the `modelcontextprotocol/modelcontextprotocol` repository. Checked 2026-10-12.

## Why we fit the direction well

The headline change is **stateful/bidirectional → stateless request/response**. platformOS
pages are already independent, per-request POSTs authenticated by a bearer token on every
call — we never held an `Mcp-Session-Id` or server session. We also never implemented
roots/sampling/elicitation (the engine calls no LLM, spec §2), and we're plain
JSON-RPC-over-HTTP POST, not the deprecated HTTP+SSE transport.

## How a request is classified (`helpers/protocol/negotiate`)

| Request | Era | Answer |
|---|---|---|
| `initialize` (any headers or `_meta`) | legacy | handshake; `params.protocolVersion` honoured if it is a supported legacy revision, else `2025-06-18` |
| `params._meta["io.modelcontextprotocol/protocolVersion"]` present | modern | header `MCP-Protocol-Version` required and equal (else 400, `-32020`); revision must be modern and supported (else 400, `-32022` with `data.supported` = modern revisions) |
| only the `MCP-Protocol-Version` header | legacy if the header names a supported legacy revision | a modern revision without `_meta` → 400, `-32020`; anything else → 400, `-32022` with the legacy revisions |
| neither | legacy, `2025-06-18` | unchanged |

## Change-by-change

| `2026-07-28` change | State |
|---|---|
| **Stateless core** — no `initialize`, version per request in `_meta` | ✅ Modern requests are recognised by the `_meta` key the spec defines. `initialize` stays for legacy clients and never selects a modern revision. |
| **`server/discover`** (servers MUST implement) | ✅ `rpc/discover`: `supportedVersions` (modern only, since a client uses them per request), capabilities including `extensions["io.modelcontextprotocol/tasks"]`, `instructions`, `ttlMs`/`cacheScope`, `_meta["io.modelcontextprotocol/serverInfo"]`. Modern requests only. The opt-in connect-time OAuth challenge (`oauth.challenge_initialize`) covers it as well as `initialize`. |
| **Version errors** — `UnsupportedProtocolVersion` (`-32022`), `HeaderMismatch` (`-32020`), both 400 | ✅ In `negotiate`. |
| **Standard request headers** — `Mcp-Method` on every request, `Mcp-Name` on `tools/call`, `prompts/get` (`params.name`) and `resources/read` (`params.uri`); Base64 sentinel `=?base64?…?=` | ✅ `helpers/protocol/check_headers`, modern requests only: missing or different → 400, `-32020`. Sentinel values are decoded first; data that is not strict padded Base64 is a malformed header. Legacy requests keep the old reconciliation (`-32600`). |
| **`resultType`** on every result | ✅ Stamped `"complete"` in `rpc/dispatch` on every modern success result; legacy results are unchanged. |
| **Cacheable results** — `ttlMs` + `cacheScope` `"public"` / `"private"` | ✅ On `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read` and `server/discover` for modern requests. `private` when the answer depends on the caller: a principal-scoped `tools/list`, and `prompts/list`, `resources/list` and `resources/templates/list` for a signed-in caller, and a `resources/read` from the app's resource provider; everything else `public`. |
| **Removed methods** — `initialize`, `ping`, `logging/setLevel` | ✅ A modern request for a method the revision does not define answers 404, `-32601` (`initialize` is served as legacy). |
| **Retired error code** `-32002` (resource not found → `-32602`) | ✅ For `resources/read`, modern requests get `-32602`. |
| **Per-request client capabilities** (`io.modelcontextprotocol/clientCapabilities`) | ◻︎ Accepted, not consumed: the server needs no client capability today. |
| **MRTR** — `resultType:"input_required"` | ◻︎ Not implemented. Needed before any server-initiated input (for example approval through URL elicitation). |
| **Tasks extension** (`io.modelcontextprotocol/tasks`, `ext-tasks` spec 2026-07-28) | ✅ See "Approval tasks" below. |
| **`x-mcp-header` / `Mcp-Param-*`** | ◻︎ Not needed: no tool declares `x-mcp-header`, so no `Mcp-Param-*` header is recognised. |
| **Auth hardening** — RFC 9207 `iss`, CIMD over DCR | ◻︎ Mostly authorization-server side; see the OAuth notes in the README. |
| **Deprecations** — Roots, Sampling, Logging; HTTP+SSE | ✅ Never had roots/sampling/SSE. `logging/setLevel` remains for legacy clients only. |
| **Earlier transports** — GET / DELETE on the endpoint | ✅ `GET /mcp` and `DELETE /mcp` answer 405 with `Allow: POST` (required for GET by 2025-06-18 when no SSE stream is offered; recommended by 2026-07-28). |

## Approval tasks (Tasks extension)

An approval-gated `tools/call` (`requires_approval: true`) is a task for a modern request
that declares `extensions["io.modelcontextprotocol/tasks"]` in its client capabilities.

- **Creation** — `tools/call` answers with a `CreateTaskResult` (`resultType: "task"`) once
  the approval row is stored. Any other client gets the pending `CallToolResult` with a
  `handle` for the built-in `mcp_approval_status` tool, as before.
- **`tasks/get`** — the `Task`: `taskId` (the approval handle, 128 random bits),
  `status`, `statusMessage`, `createdAt`, `lastUpdatedAt`, `ttlMs: null` (approval rows are
  kept), `pollIntervalMs` (`defaults.task_poll_interval_ms`, 30 s), and `_meta
  ["com.platformos.mcp/approval"]` with the tool name and approval deadline.
- **Status mapping** (`helpers/tasks/present`):

  | Approval | Task |
  |---|---|
  | pending (window open), approved (running) | `working` |
  | executed | `completed`, `result` = the tool result |
  | failed after the handler ran (handler error, rolled-back write) | `completed`, `result` with `isError: true` |
  | failed before the handler ran (tool gone `-32602`, arguments invalid `-32602`, forbidden `-32001`) | `failed`, `error` |
  | rejected by an operator, withdrawn by the requester | `cancelled`, with the reason in `statusMessage` |
  | expired, or pending past its deadline | `failed`, `error` `-32005` |

  The stored `result_json` / `error_json` are exactly what the inline call would have
  answered (`approval/execute`). Rows decided before these columns existed fall back to
  `result_summary`.
- **`tasks/update`** — approval tasks never enter `input_required` (an operator decides,
  not the client), so `inputResponses` are ignored and the request is acknowledged with an
  empty result. It can never approve or reject.
- **`tasks/cancel`** — withdraws a pending approval under the row lock; acknowledged with
  an empty result whether or not the task was still pending (cooperative cancellation).
- **Errors** — not declared → 400 `-32021` naming the extension; unknown or another
  principal's task → `-32602` "Task not found"; no bearer → 401 `-32001`. `Mcp-Name` must
  equal `params.taskId`.
- **Not implemented** — `notifications/tasks` over `subscriptions/listen` (optional; the
  server has no streaming).

## Files

- `helpers/protocol/negotiate` — era + revision, version errors.
- `helpers/protocol/check_headers` — `Mcp-Method` / `Mcp-Name` for modern requests.
- `helpers/protocol/cache_hint` — `{ttlMs, cacheScope}` from config.
- `commands/rpc/dispatch` — transport checks, negotiation, header checks, `resultType`.
- `commands/rpc/route` — method routing per era.
- `commands/rpc/discover`, `commands/rpc/initialize`, `queries/instructions` (shared text).
- `commands/rpc/tasks_{get,update,cancel}`, `commands/tasks/{find_owned,present}`,
  `commands/approval/execute` (stores the outcome), `views/pages/mcp-{get,delete}`.
- `config` — `supported_protocol_versions`, `modern_protocol_versions`, `cache.*_ttl_ms`.
- Tests — `conformance.test.mjs › protocol eras` and `coverage.test.mjs › Tasks —`;
  the modern client is `makeModern` in `tests/lib/harness.mjs`.

## Remaining checklist

1. **MRTR** — `input_required` results, prerequisite for elicitation-based approval.
   Deferred on purpose (2026-10-12): no engine or app feature asks the client for input
   yet, so it is built together with its first user — approval through URL elicitation —
   rather than as unused protocol code.
2. **`notifications/tasks`** — only if the server ever offers `subscriptions/listen`.
   Blocked: platformOS pages answer one request and cannot hold a stream open.

## Non-goals

- HTTP+SSE transport (deprecated; never offered).
- Roots / Sampling (deprecated; the engine calls no LLM by design, §2).
